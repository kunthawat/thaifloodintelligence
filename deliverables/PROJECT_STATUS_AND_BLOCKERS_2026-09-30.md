# Thailand Flood Intelligence — สถานะระบบและรายการข้อขัดข้อง

ตรวจ ณ วันที่ 30 กันยายน 2569 เวลาประมาณ 15:05–15:08 น. (เวลาไทย) โดยอ่านสถานะ API, ฐานข้อมูล, health check ของแหล่งข้อมูล และโค้ดที่ถูกเรียกจริงจากหน้าแอป

ซอร์ส ณ revision `59bd1da` (`Restore detailed aligned river network`) ซึ่ง push ไปยัง Gitea แล้ว

## สรุปสำหรับผู้ใช้

หน้าแอป แผนที่ การค้นหาตำบล ฐานข้อมูล และ API ทำงาน แต่ **ยังไม่มีผลคำนวณระดับความเสี่ยงน้ำท่วมที่ผ่านเกณฑ์** ข้อความ “ยังประเมินไม่ได้” จึงไม่ได้แปลว่าระบบล่มหรือไม่มีน้ำท่วม แต่หมายถึงระบบยังไม่มีข้อมูลและแบบจำลองที่ยืนยันได้พอจะบอกว่าเสี่ยงหรือไม่เสี่ยง

มีสาเหตุสำคัญสองชั้น:

1. API พยากรณ์ที่หน้าแอปเรียกยังเป็นโครงเริ่มต้น `build_forecast()` ซึ่งคืนค่า `null` และ `eligible=false` สำหรับความน่าจะเป็น เวลา ระดับสูงสุด และความลึก โดยไม่มีการคำนวณจากข้อมูลจริง
2. ข้อมูลสถานีที่มีอยู่ให้ได้เพียงหลักฐานประกอบบางส่วน: ประกาศเตือน DWR ล้าสมัย, ฝนสถานีถูกระบุว่าใช้เป็นค่าบังคับแบบจำลองไม่ได้, ไม่มีเกณฑ์น้ำล้นตลิ่ง/กราฟระดับ-ปริมาตร และไม่มีเหตุการณ์น้ำหรือแบบจำลองที่สอบเทียบแล้ว

**ห้ามอ่านสถานะ UNKNOWN/ไม่ทราบว่าเป็นหลักฐานว่าน้ำท่วมไม่มี** แอปยังใช้เป็นระบบเตือนภัยเชิงปฏิบัติการไม่ได้จนกว่าจะต่อข้อมูลและการคำนวณที่ขาดให้ครบและตรวจสอบผ่าน

## ผลตรวจพื้นที่ตัวอย่าง: อำเภอบ้านโป่ง จังหวัดราชบุรี

ตำแหน่งทดสอบถูกจับคู่กับตำบลเบิกไพร อำเภอบ้านโป่ง จังหวัดราชบุรี ระบบพบลุ่มน้ำและสถานีใกล้เคียง การค้นคำว่า “เบิกไพร” คืนสองตำบลชื่อซ้ำพร้อมอำเภอ/จังหวัดกำกับ จึงเลือกพื้นที่ได้แยกกัน

จุดจากผลค้นหาตำบลเป็นจุดอ้างอิงภายในขอบเขตตำบล ไม่ใช่พิกัดบ้านหรืออาคาร ระบบยังไม่ได้ทำ geocoding ระดับเลขที่บ้าน

| สถานการณ์ | READY; สถานีระดับน้ำใกล้ 3 แห่ง, สถานีฝนใกล้ 5 แห่ง; มีขอบเขตตำบลและลุ่มน้ำ | มีข้อมูลประกอบพื้นที่ แต่ยังไม่จำแนกความเสี่ยง |

ข้อมูลสถานีฝนตัวอย่าง: สถานีใกล้สุดรายงาน 51.4 มม./24 ชม. และ 0.0 มม./1 ชม. ณ เวลาที่แหล่งข้อมูลรายงาน ค่านี้เป็นค่าของสถานี ไม่ใช่การตรวจวัดตรงตำแหน่งค้นหา และระบบไม่ควรแปลงค่านี้เป็นโอกาสน้ำท่วมโดยไม่มี trigger/แบบจำลอง

## สาเหตุเชิงโค้ดที่ทำให้ยังประเมินไม่ได้

### 1. API พยากรณ์ยังเป็น placeholder

`app/models/forecast.py` ระบุผลลัพธ์ทั้งหมดเป็นค่า null/ไม่ผ่านเกณฑ์โดยตรง และมีคำอธิบายว่าไม่มี provider, observations, graph หรือ calibrated model ใน initial project คำอธิบายส่วน “ไม่มี observations/graph” ล้าสมัยแล้ว เพราะปัจจุบันมีสถานีและ GIS บางส่วน แต่ไม่มี calibrated forecast model และ valid model inputs `GET /v1/location/risk` และ `GET /v1/location/forecast` เรียกฟังก์ชันนี้ จึงไม่สร้างความน่าจะเป็นหรือคำตัดสินจริงจากข้อมูลที่ ingest มา

นอกจากนี้ `GET /v1/location/risk` กำหนด `risk_level=UNKNOWN` และเหตุผล `INSUFFICIENT_VALID_OBSERVATIONS` ให้ทุกภัยแบบคงที่ แม้ readiness รายจุดจะพบสถานีใกล้ 3–5 แห่งและคืน evidence บางส่วนแล้ว ส่วน `/v1/location/explanation` ก็คืนเหตุผลข้อจำกัดแบบกำหนดตายตัว จึงยังไม่แยกชัดว่าอะไรคือ “มี observation แต่ยังไม่มีเกณฑ์/แบบจำลอง” กับ “ไม่มี observation จริง”

การต่อแหล่งข้อมูลเพิ่มอย่างเดียวจึงยังไม่ทำให้เกิดคำพยากรณ์ ต้องนำข้อมูลที่ผ่าน semantic/quality gate ไปเข้า risk/forecast model ที่มีเกณฑ์และ calibration ก่อน

### 2. คำว่า READY ในระดับระบบไม่ใช่คำยืนยันความเสี่ยง ณ จุด

`/v1/data-quality` รายงาน `DATA_PLATFORM_READY=true`, `MAP_READY=true`, `SITUATION_REPORT_READY=true`, `HAZARD_ONLY_READY=true`, แต่ `GLOBAL_HAZARD_STATUS=PARTIAL`, `QUANT_FORECAST_READY=false`, `POINT_DEPTH_READY=false` และบอกว่าไม่มี current scoped warning กับไม่มี numeric rainfall model input

สาเหตุคือโค้ดนิยาม `HAZARD_ONLY_READY` ว่าเป็นจริงเมื่อสถานะรวมเป็น READY **หรือ PARTIAL** ดังนั้นคำนี้หมายถึงมีหลักฐานให้ระบบประเมินบางส่วน ไม่ได้หมายถึงพื้นที่ที่เลือกได้รับคำประเมินน้ำท่วมแล้ว ชื่อดังกล่าวชวนให้เข้าใจผิดและควรแยกสถานะ/ป้ายให้ชัด

### 3. สัญญาณที่มีเป็นเพียงหลักฐานบางส่วน

- **ระดับน้ำ:** ThaiWater ตอบได้ 806 สถานี และมีค่า MSL 806 สถานี; จุดตัวอย่างมีสถานีใกล้ 3 แห่ง โดยพบความเชื่อมโยงกับ reach แต่ไม่ทราบระดับตลิ่ง/เกณฑ์เตือนที่สอบเทียบกับสถานีนั้น
- **ฝน:** ThaiWater ตอบได้ 4,379 สถานีและค่าฝน 24 ชม.; จุดตัวอย่างมี 5 สถานีในระยะกรอง connector ตั้ง `rainfall_usable=false` ไว้โดยตรง และระบุ timezone semantics เป็น UNVERIFIED จึงไม่มี verified numeric model input
- **คำเตือน:** DWR อ่านหน้าได้และ parse รายงานได้ 59 รายการ แต่ข้อมูลล่าสุดที่พบคือ 29 ก.ย. 21:00 น. จึงจัดเป็น `STALE_CONTEXT_ONLY`; พื้นที่ตัวอย่างไม่มีคำเตือนปัจจุบันที่ยืนยันได้

## งานที่ยังขาด เรียงตามผลกระทบ

### P0 — ต้องทำก่อนเชื่อผลประเมินน้ำท่วม

1. แทนที่ `build_forecast()` placeholder ด้วย risk/forecast path จริงที่กิน readiness/evidence และคืนเหตุผล eligibility รายภัย/ราย output
2. กำหนดและสอบเทียบเกณฑ์ระดับน้ำ/ระดับตลิ่งรายสถานีหรือ reach พร้อม datum, station–reach mapping และช่วงความสดของข้อมูล
3. ทำเส้นทางฝนที่ใช้กับแบบจำลองได้จริง: แก้ TMD QPE discovery/404 หรือยืนยันแหล่งสำรอง, ตรวจหน่วย/เวลา/CRS/coverage และเปิด `rainfall_usable` เมื่อผ่านหลักฐานเท่านั้น
4. เพิ่มข้อมูลความชื้น/ฝนก่อนหน้าและเกณฑ์กระตุ้นน้ำป่า พร้อมประเมิน runoff ตาม catchment
5. เชื่อม warning/event กับขอบเขตพื้นที่และเวลาที่ถูกต้อง; แก้ความสด DWR และปลายทาง station 404

### P1 — เพื่อเวลา ระดับสูงสุด และการรับผลกระทบ ณ จุด

1. เพิ่มเหตุการณ์/คลื่นน้ำต้นน้ำและ trajectory ที่ตรวจสอบได้ พร้อมแบบจำลองเวลาเดินทาง
2. นำเข้า bank references และกราฟ stage–storage/transfer ที่ยืนยันแหล่งและ datum
3. ปรับความละเอียด terrain/การระบายและ hydraulic connectivity สำหรับการประเมินจุด; ผล DEM ปัจจุบันยังไม่พอสำหรับ point depth
4. เพิ่มสถานะประตู/เขื่อน/เครื่องสูบและเงื่อนไขขอบเขตปลายน้ำที่ตรวจสอบแล้ว
5. ทำเส้นทาง tide-to-river เฉพาะพื้นที่ชายฝั่ง และใช้ `NOT_APPLICABLE` สำหรับ hazard ที่ไม่เกี่ยวกับพื้นที่นั้น
6. ทำ location query กับ LDD และข้อมูลดิน/land use หากจะใช้เป็นหลักฐานใน runoff/wetness

### P2 — ความน่าเชื่อถือ/การนำไปใช้

1. เปลี่ยนชื่อ `HAZARD_ONLY_READY` หรือแสดง scope ให้ผู้ใช้เห็นว่าเป็น platform/global partial ไม่ใช่ผลรายจุด
2. ทำ freshness labels ให้สอดคล้องกับ timestamps และแยก `NOT_APPLICABLE` ออกจาก `NOT_READY`
3. นำเข้า DPM major basins หากจำเป็นกับการจับคู่/รายงานตามลุ่มน้ำหลัก
4. ทบทวนสิทธิ์ใช้งานเชิงพาณิชย์ของ HII และแหล่งข้อมูล GIS ก่อน deploy เชิงพาณิชย์
5. รัน acceptance/regression suite หลังพัฒนา readiness และ model; การตรวจรอบรายงานนี้ใช้ live API/health และ code inspection ยังไม่ได้รัน automated test suite

## งานที่ทำเสร็จในโปรเจกต์แล้ว

- ทำแอปแบบ local สำหรับ Windows ใช้ PostgreSQL/PostGIS แบบ portable ได้โดยไม่ต้องพึ่ง Docker
- เชื่อมแผนที่ MapLibre/OpenFreeMap และ API สำหรับตำแหน่ง ข้อมูลสถานี readiness และ data quality
- นำเข้าขอบเขต DPM เพื่อค้นชื่อตำบล; ชื่อซ้ำแสดงอำเภอ/จังหวัดช่วยเลือกพื้นที่
- นำเข้า HydroBASINS, HydroRIVERS และ HydroSHEDS DEM/flow direction/flow accumulation
- นำเข้า DPM ลำน้ำหลักและสายรองครบ; แก้ MapLibre style expression ที่ทำให้ชั้นลำน้ำไม่ถูกวาด
- แผนที่เปิดชั้นโครงข่ายลำน้ำไว้; DPM ใช้เป็นแนวอ้างอิง ส่วน HydroRIVERS เป็น topology ธรรมชาติ แผนที่ฐาน OpenFreeMap/OpenStreetMap เป็นอีกชุดข้อมูล จึงยังอาจมีความต่างของเส้นเล็กน้อยจากมาตราส่วนและเวลาปรับปรุงข้อมูลที่ไม่เหมือนกัน
- มี readiness แยกตามภัยและ output และป้องกันการแสดงเลขพยากรณ์เมื่อไม่ผ่านเงื่อนไข
- มี connector/source health, cached station readings, warning scope และเหตุผลข้อมูลไม่พร้อม
- มีเอกสาร master spec, data manifest, recovery plan, README, migrations และ regression fixtures ในซอร์ส

## การตรวจสอบที่ทำในรอบนี้

- `/health`: สถานะ `ok`, database `READY`, migration ครบ
- `/v1/location/readiness`: พื้นที่ตัวอย่าง `PARTIAL / EVIDENCE_ONLY`; สถานการณ์สถานี `READY`
- `/v1/location/risk`: UNKNOWN, probability null, occurrence ineligible
- `/v1/location/forecast`: forecast outputs ไม่ผ่าน eligibility; ไม่มีเส้น forecast
- `/v1/data-quality`: probes แหล่งข้อมูล 23 รายการและแสดง blockers ข้างต้น
- `/v1/places/search?q=เบิกไพร`: คืนผล 2 ตำบลแยกอำเภอ ถูกพื้นที่
- สุขภาพฐานข้อมูล: 20 migrations, 585,257 basins, 1,428,959 network edges, 3 terrain products, 7,658 tambon codes, 868,800 DPM waterways

## ขอบเขตไฟล์ ZIP

ZIP นี้เป็น **source bundle พร้อมเอกสารสรุป** ประกอบด้วยโค้ดแอป, SQL migrations, scripts, connectors, tests/fixtures, config, README และเอกสารสเปก/แผนกู้คืน รวมถึงรายงานฉบับนี้

เพื่อไม่เผยแพร่ข้อมูลลับหรือสร้าง ZIP หลาย GB จะไม่รวม `.env`, `.git`, `.venv`, `local_runtime/` (ฐานข้อมูล รหัสผ่าน runtime และ logs), ไฟล์ GIS ที่ดาวน์โหลดไว้ใน `data/static/` และ cache/compiled files ดังนั้น ZIP ไม่ใช่ backup ฐานข้อมูล; การตั้งเครื่องใหม่ต้องเตรียม PostGIS และดาวน์โหลด/นำเข้าชุด GIS ตาม README อีกครั้ง
